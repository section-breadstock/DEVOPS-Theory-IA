# Before and After: Vulnerable vs Fixed Image Comparison

This document compares the two controlled images built from the same application source with different
lodash dependency versions. All numbers below come from **actual Trivy scans** that were run during
implementation. Where a value depends on a CI run.

## How to compare the results

1. **Local (Docker + Trivy CLI or the pinned Trivy container):** run `scripts/demo.ps1`. JSON reports are written to `reports/`.
2. **GitHub Actions:** run the workflow twice with `workflow_dispatch` (`scenario = vulnerable`, then `scenario = fixed`).
   Download the `trivy-report-vulnerable` and `trivy-report-fixed` artifacts from each run.
3. Open each JSON file and read `Results[].Vulnerabilities[]`. For each entry, note `PkgName`,
   `InstalledVersion`, `FixedVersion`, `VulnerabilityID`, and `Severity`.
4. Compare the High and Critical counts and the gate result (the job conclusion of the
   `Security gate` step: failed = non-zero exit, passed = exit 0).

Useful one-liner for counting qualifying findings in a downloaded report (PowerShell):

```powershell
$r = Get-Content .\trivy-report-vulnerable.json -Raw | ConvertFrom-Json
$r.Results | ForEach-Object { $_.Vulnerabilities } | Where-Object { $_ } |
  Group-Object Severity | Select-Object Name, Count
```

| Target | Package | Installed | Fixed in | CVE | Severity | Title |
|---|---|---|---|---|---|---|

| app/package.json | lodash | 4.17.20 | 4.18.0 | CVE-2026-4800 | HIGH | lodash: Arbitrary code execution via untrusted input in template imports |

## Fixed image findings (actual scan output)

The same scan on `trivy-demo:fixed` reports **no** High or Critical library findings (the only target,
`app/node_modules/lodash/package.json`, is clean).

## Why the vulnerable image fails and the fixed image passes

- **Vulnerable:** `lodash@4.17.20` is below the fixed version of CVE-2021-23337 (4.17.21) and of CVE-2026-4800
  (4.18.0). Both are HIGH severity, so the enforcement step (`severity: HIGH,CRITICAL`, `exit-code: 1`) returns non-zero.
- **Fixed:** `lodash@4.18.1` is at or above every fixed version reported for these CVEs, so no qualifying finding is
  reported and the enforcement step returns 0.

## Important observation: a 4.17.21 "fix" was not enough

The first remediation attempt used lodash 4.17.21, which is the fix for CVE-2021-23337. A real scan of that image
still reported **CVE-2026-4800** (HIGH, fixed in 4.18.0), so the gate would still have failed. The fixed configuration
was therefore moved to 4.18.1. This is the reason the project verifies with real scans instead of assuming a version
is clean.

The scan also initially reported HIGH findings in npm's own bundled packages (`brace-expansion`, `undici`,
`http-cache-semantics`) that are shipped inside the `node:24-alpine` base image rather than in the application. The
runtime stage now removes the npm and corepack tooling, which the service does not need. Those findings no longer appear
in the fixed scan.

## Remediation applied

| Change | File | Reason |
|---|---|---|
| lodash `4.17.20` -> `4.18.1` (exact pin, lockfile regenerated by npm) | `package.json`, `package-lock.json` | Removes CVE-2021-23337 and CVE-2026-4800 |
| Vulnerable config kept at lodash `4.17.20` | `vulnerable/package.json`, `vulnerable/package-lock.json` | Controlled demonstration only |
| Runtime image drops npm/npx/corepack | `Dockerfile` (runtime stage) | Removes unused third-party packages with HIGH findings |

## Notes and limitations

- Findings depend on the Trivy vulnerability database at scan time. Re-running a scan later may show different results.
- The GitHub Action (`aquasecurity/trivy-action@v0.36.0`) uses Trivy v0.76.0 by default, which matches the local scan above.
  Its vulnerability database is downloaded when the workflow runs.
- Only library (application-dependency) findings are gated, as required. OS-package findings are excluded by `--vuln-type library`.
